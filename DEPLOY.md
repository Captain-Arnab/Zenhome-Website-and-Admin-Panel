# Zen Home Experts – deployment guide

Website (PHP pages in the project root), customer/app API (`api/`), admin
panel (`admin/` + `api/admin/`). PHP 8.1+ (tested on 8.2) and MySQL/MariaDB.
This file is blocked from the web by `.htaccess`.

## 1. Before you start

1. Back up the database: `mysqldump -u USER -p DBNAME > zencare_before_deploy.sql`
   and move/save that file **outside the web root** (e.g. a dedicated backup
   host path, not inside this project folder). Never leave a dump under
   `database/backups/` on the live server for longer than it takes to copy it
   off - that folder is git-ignored and blocked by `.htaccess`
   (`RedirectMatch 404 /(...|backups?|...)`) as a second layer of protection,
   not as the primary place to keep backups.
2. Back up the current site folder.
3. See "Rollback" (section 11) for how to restore this backup if a deploy
   needs to be undone.

## 2. Upload the files

Upload the whole project **except** `.env` (keep the server's own copy),
`logs/*.log`, `cron/last_run.json`, `cron/*.lock`, `cron/*.log`, and any local
database backup (`database/backups/`, `*.sql`) - see `.gitignore` for the full
list. `vendor/` must be uploaded (or run `composer install --no-dev` on the
server from `api/composer.json`).

This is a file-copy deployment (rsync/FTP/SFTP), not a `git pull` on the
server, so `uploads/`, `api/uploads/` and `assets/services/` (user-uploaded
content, git-ignored because it changes constantly and partner KYC documents
must never sit in source control) still need to be copied or kept in sync
separately - they are not reconstructed by cloning the repo. New installs:
`uploads/admin/*` is regenerated by the seed scripts in section 5; existing
admin uploads and `api/uploads/partners/*` (KYC documents) must be migrated
by copying the folder, not by git.

## 3. `.env` keys (project root)

Names only – fill the values on the server. Unknown/empty optional keys keep
the default behaviour. **After changing `.env`, restart PHP** (reload/restart
Apache with mod_php, or restart PHP-FPM) - `vlucas/phpdotenv`'s `safeLoad()`
does not overwrite values already loaded into a long-running worker process,
so a persistent worker keeps serving the old values until it restarts.

| Key | Required | Purpose |
|---|---|---|
| `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` | yes | Database (used by `api/db.php` and every endpoint) |
| `PHONEPE_CLIENT_ID`, `PHONEPE_CLIENT_SECRET`, `PHONEPE_CLIENT_VERSION`, `PHONEPE_ENV`, `PHONEPE_MERCHANT_ID` | yes | PhonePe v2 checkout (`api/phonepe_client.php`) |
| `APP_URL` | yes | Canonical site base URL (`https://zenhomeexperts.com`), the one place to change the domain - `api/runtime.php`'s `app_url()` helper reads it |
| `PHONEPE_REDIRECT_URL`, `PAYMENT_CALLBACK_BASE_URL` | yes | Payment return URLs |
| `PHONEPE_WEBHOOK_USERNAME`, `PHONEPE_WEBHOOK_PASSWORD` | yes (for webhooks) | Must match the username/password set in the PhonePe dashboard (Developer Settings > Webhook, Authentication Type: SHA); verified by `api/payment_webhook.php`. Webhook URL to register: `https://zenhomeexperts.com/api/payment_webhook.php` (update this in the PhonePe dashboard yourself - the app never calls PhonePe to change it) |
| `APP_TIMEZONE` | recommended | e.g. `Asia/Kolkata` |
| `ADMIN_SECRET` | optional | `Admin-Token` header for the old `api/admin/*.php` endpoints; empty = disabled |
| `SMS_ENABLED`, `SMS_GATEWAY_URL`, `SMS_GATEWAY_USER`, `SMS_GATEWAY_PASSWORD`, `SMS_GATEWAY_SENDER`, `SMS_GATEWAY_PEID` | optional | Admin notifications / SMS campaigns |
| `REVIEWS_AUTO_APPROVE` | optional | `true` publishes app reviews without moderation (default `false`) |
| `LEGACY_STRICT_AUTH` | optional | `true` = legacy app endpoints require the customer login token and only allow the customer's own data (default `false` = unchanged) |
| `LEGACY_ASSIGN_STRICT` | optional | `true` = `api/admin/assignTechnician.php` assigns only the given booking and sends the OTP by SMS instead of returning it (default `false` = unchanged) |
| `APP_DEBUG` | optional | `true` shows PHP errors in the browser – **never in production** (default `false`) |
| `APP_LOG_DIR` | optional | Absolute folder for `php_errors.log`, ideally outside the web root (default `logs/`, blocked from the web) |
| `RECEIPT_BASE_URL` | optional | Receipt link prefix used by `api/user_transaction.php`; when empty it falls back to `https://<request host>/api/order_details.php?order_id=` |

## 4. Database migrations (in this order)

`php database/migrate.php` applies every pending file in name order and
records it in `schema_migrations` (re-running is safe; `--status` lists them).

1. `2026_10_03_001_admin_panel.sql` – admin users/sessions, roles, audit log, booking/professional columns
2. `2026_10_03_002_checkout_coupons_scheduler.sql` – coupons, scheduled notifications / SMS
3. `2026_10_03_003_catalog_website.sql` – website catalog columns (categories, services, banners)
4. `2026_10_03_004_password_resets.sql` – customer password reset OTPs
5. `2026_10_03_005_site_settings_packages_legacy_log.sql` – `site_settings`, `home_packages`, category `long_description`/`faqs`, `legacy_access_log`
6. `2026_10_03_006_service_partners_final_consent.sql` – `service_partners.final_consent` (fixes `api/partner_registration.php` inserting a column that didn't exist)
7. `2026_10_03_007_reviews_featured.sql` – `ratings_feedback.featured` (Admin > Reviews can feature a review on the homepage)
8. `2026_10_03_008_category_why_process_cta.sql` – category `why_html`/`process_html`/`cta_html` paragraph overrides

All migrations are additive (new tables / nullable columns / indexes); no
existing column is dropped or changed.

## 5. Seeds (run once, safe to re-run)

```
php database/seed_catalog_from_website.php --dry-run   # preview
php database/seed_catalog_from_website.php             # categories, services, banners + images
php database/seed_site_content.php --dry-run
php database/seed_site_content.php                     # site settings, Smart Packages, category intro text
```

Both only fill missing data, so edits made in the admin panel are kept.
First admin login / password recovery: `php database/admin_password.php --list`
and `php database/admin_password.php EMAIL`.

## 6. Cron

Scheduled notifications and SMS campaigns, every 5 minutes:

```
*/5 * * * * /usr/bin/php /path/to/site/cron/send_scheduled.php >> /path/to/site/cron/send_scheduled.log 2>&1
```

## 7. Folder permissions

Writable by the PHP user (e.g. `755` folders / `644` files, owner = PHP user;
avoid `777`):

- `uploads/` (admin uploads go to `uploads/admin/<module>/`)
- `api/uploads/` (partner documents from `api/partner_registration.php`)
- `assets/services/` (images uploaded by the old admin app)
- `logs/` (PHP error log, unless `APP_LOG_DIR` is set)
- `cron/` (lock file, `last_run.json`, run log)

Everything else can be read-only. Keep `.htaccess` files in `uploads/`,
`uploads/admin/`, `api/uploads/`, `assets/services/`, `logs/`, `cron/`,
`api/admin/core/` and `api/admin/modules/`.

## 8. PHP extensions

`pdo_mysql`, `mysqli`, `gd` (with WebP support), `fileinfo`, `curl`,
`mbstring`, `openssl`, `json`, `zip` (backups only). Apache with
`mod_rewrite`/`mod_alias`, `mod_headers` and `AllowOverride All` (or at least
`FileInfo Options AuthConfig Limit`).

Error display: `.htaccess` turns `display_errors` off under mod_php; PHP-FPM /
CGI hosts read `.user.ini`. `api/runtime.php` logs errors to `logs/` (or
`APP_LOG_DIR`).

## 9. Post-deploy checks

1. `php database/migrate.php --status` – all migrations applied (see section 4
   for the current count/order).
2. Open the homepage and every category page (`ac-service.php`,
   `carpenter-service.php`, `home-cleaning.php`, `salon.php`,
   `pest-control.php`, `washing-machine-repair.php`, `chimney-repair.php`,
   `water-purifier.php`, `refrigerator-repair.php`), plus `services.php`,
   `contact.php`, `about-us.php`, `faq.php`, `cart.php`, `checkout.php`,
   `login.php`, `register.php` – all 200, no PHP/JS errors, images load.
3. Admin: log in at `/admin/`, open every module in the sidebar (Dashboard,
   Bookings, Categories, Subcategories, Services, Smart Packages, Banners,
   CMS Pages, Coupons, Customers, Professionals, Payments, Reviews, Locations,
   Support Tickets, Notifications, SMS, Reports, Admins, Site Settings) and
   confirm each list loads with no error (empty lists are fine).
4. These URLs must return **403 or 404**: `/.env`, `/.env.example`,
   `/.htaccess`, `/.gitignore`, `/composer.json`, `/composer.lock`,
   `/DEPLOY.md`, `/vendor/autoload.php`, `/database/migrate.php`,
   `/database/backups/` (and any file inside it), `/cron/send_scheduled.php`,
   `/logs/php_errors.log`, `/tests/` (and any file inside it),
   `/api/admin/core/bootstrap.php`, any `*.sql` / `*.bak` / `*.zip` file
   anywhere in the project.
5. Response headers of the homepage include `X-Content-Type-Options: nosniff`,
   `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`.
6. An uploaded image URL (e.g. `/uploads/admin/banners/...webp`) loads. If the
   host does not allow `Options` in `.htaccess` (500 error), remove the
   `Options -Indexes -ExecCGI` line from the upload folders' `.htaccess`.
7. Public API: `api/site_settings.php`, `api/home_packages.php`,
   `api/catalog_categories.php` return JSON with `"statusCode":200`.
8. Book a test service on the website (login, cart, checkout) up to the
   PhonePe page. Do not complete a real payment against production PhonePe
   credentials as a "test" - use a PhonePe UAT/sandbox merchant for that.
9. PhonePe webhook: in the PhonePe dashboard, send a test webhook delivery (or
   `php tests/phonepe_webhook_test.php` locally, which stubs the signature
   check and never calls PhonePe) and confirm `logs/php_errors.log` shows a
   `[payment_webhook]` line with an honest status (`ok`, `duplicate`,
   `unknown_order` or `invalid_signature`) - never a silently-swallowed error.
10. Check `logs/php_errors.log` (or `APP_LOG_DIR`) for new errors.
11. Compare `.env.example` against the server's real `.env`: every key in one
    should exist in the other (names only - never copy real values between
    them).

## 10. Legacy endpoint usage (before enabling `LEGACY_STRICT_AUTH`)

Every call to the legacy app endpoints is recorded in `legacy_access_log`.
After 1–2 weeks:

```sql
SELECT endpoint, token_state, COUNT(*) AS calls, MAX(created_at) AS last_call,
       COUNT(DISTINCT ip) AS ips
FROM legacy_access_log
WHERE created_at > NOW() - INTERVAL 14 DAY
GROUP BY endpoint, token_state
ORDER BY endpoint, token_state;

-- which clients (app vs website) call an endpoint
SELECT endpoint, LEFT(user_agent, 60) AS client, COUNT(*) AS calls
FROM legacy_access_log GROUP BY endpoint, client ORDER BY endpoint, calls DESC;
```

If every endpoint the apps use is called with `token_state = 'valid'`, set
`LEGACY_STRICT_AUTH=true`. Calls rejected in strict mode are logged with
outcome `denied_401` / `denied_403` / `denied_404`. Old rows can be removed
with `DELETE FROM legacy_access_log WHERE created_at < NOW() - INTERVAL 90 DAY`.

## 11. Rollback

If a deploy needs to be undone:

1. **Stop traffic reaching the broken code** if possible (maintenance page /
   revert the web server to the previous release folder) before touching the
   database, so nothing writes against a schema the old code doesn't expect.
2. **Restore the database** from the backup taken in step 1:
   ```
   mysql -u USER -p DBNAME < /path/outside/webroot/zencare_before_deploy.sql
   ```
   This is a full restore (it recreates every table from the dump), so only
   do it when rolling back to the exact point the backup was taken at - any
   orders/bookings/payments made after that backup are lost from the DB
   (they may still exist at PhonePe; reconcile manually via Admin > Payments
   and the PhonePe dashboard if needed).
3. **Restore the previous code release** (the file backup from step 1.2, or
   your previous deployed folder / git tag).
4. Run `php database/migrate.php --status` against the restored database to
   confirm it matches what the restored code expects. If the restored DB is
   older than the restored code's migrations, either apply the missing
   migrations (they are additive and safe to re-run) or restore an older code
   version that matches.
5. Restart PHP (see the `.env` note in section 3) and re-run the section 9
   post-deploy checks.

A partial rollback (keep the new database, revert only the code, or vice
versa) is riskier because the migrations are additive but the PHP code is
not always backward-compatible with a newer schema it doesn't know about -
prefer matching code and database versions.

## 12. Admin user guide - what each module controls

A quick map from the admin sidebar to what changes on the public website.
Every change here takes effect on the next page load - nothing needs a
redeploy.

| Admin module | Controls |
|---|---|
| **Dashboard** | Read-only overview (booking counts, payment totals, charts). Nothing to edit here. |
| **Bookings** | Every customer booking: assign a professional, change status, cancel, add internal notes, mark cash bookings as paid. Status and assignment changes are what the customer's "My Bookings" screen and SMS (when `SMS_ENABLED=true`) reflect. |
| **Categories** | The 9 service category pages and any admin-added category (served by `service-category.php`): name, images, website text (tagline, card label, highlights, long description, FAQs, and the "why choose us" / "how it works" / CTA paragraphs), and which slug/page it uses. Disabling a category hides it and its services from the website immediately. |
| **Subcategories** | Groupings under a category (used to organise services); same active/inactive behaviour. |
| **Services** (Smart Packages / SaverPacks) | Individual bookable services: price, description, image, which category/subcategory. Disabled services disappear from category pages and search. |
| **Smart Packages** (Home Packages) | The homepage "Smart Packages" cards - link to a category, a specific service, or a custom URL. |
| **Banners** | Homepage hero/slider/promotional images and their links, with optional start/end dates. |
| **CMS Pages** | Freeform content pages (e.g. policy pages) rendered by slug. |
| **Coupons** | Discount codes: type (percentage/flat), value, min order, validity window, usage limits. Applied at checkout/booking and tracked per customer. |
| **Customers** | Customer accounts: view activity, spend, bookings; deactivate/reactivate. |
| **Professionals** | Service partner records: approve/reject registrations (`api/partner_registration.php` submissions land here as "Pending"), activate/deactivate, edit details. Only active, approved professionals can be assigned to a booking. |
| **Payments** | Read-only transaction list and per-booking invoice (now pulls the company address from Site Settings instead of a hardcoded city). Refund tracking (status/amount/note) for Super Admins. |
| **Reviews** | Customer ratings/feedback: approve or hide a review (hidden reviews never show publicly), and mark an **Approved** review "Featured" to show it in the homepage testimonials section. The homepage falls back to its built-in testimonials until at least 3 reviews are featured. |
| **Locations** | Cities and serviceable areas/pincodes (active flag, sort order). Feeds the homepage "Service Areas" list directly - inactive areas/cities are never shown and never offered at checkout. |
| **Support Tickets** | Customer support conversations raised from the app/website. |
| **Notifications** | One-off or scheduled customer notifications/campaigns (in-app and SMS, when enabled). |
| **SMS** | SMS templates and gateway settings/test send. |
| **Reports** | Read-only exports (bookings, payments, customers, services, professionals, by date). |
| **Admins** | Admin user accounts and roles (Super Admin only). |
| **Site Settings** | Company name, contact details, address, social/app links, logo/favicon/section images, and the Homepage/Footer text groups (hero label/subtitle/rating/bookings badge, footer CTA, trust strip, footer "Service Area" caption). A field left empty uses its documented default; an image left empty/invalid falls back to the built-in asset. |
